## 1. Identifiers
- Format: `<prefix>_<ULID>` (26-char Crockford base32, upper case), e.g. `agt_01JA2...`. Prefixes: `acc` account, `per` person, `ws` workspace, `agt` agent (card), `con` agent connection, `ins` app instance, `brg` bridge, `rel` release, `lic` licence, `off` offer, `ord` order, `edg` canvas edge, `drf` draft, `dev` device-flow request, `aud` audit event, `hld` hold, `rcp` receipt, `call` bridge call id, `osn` owner CLI/native session, `lnk` provider (Railway) link.
- Product id = manifest `id`: lower-kebab slug, 2–32 chars (`^[a-z][a-z0-9-]{1,31}$`). Product ids are data; no code path branches on a product id.
- opt2: at most ONE instance of a product per workspace (licence = one workspace per product). Paths may therefore use the product id inside a workspace (`/a/<product>/…`).
- Person ↔ account: 1:1 in opt2 (account owner). Both ids exist so members can come later without a format change.

## 2. Audience / subject format (ONE format)
`tb:<kind>:<id>` where kind ∈ `portal | per | agt | ins | brg`. Examples: `tb:portal`, `tb:agt:agt_01…`, `tb:ins:ins_01…`, `tb:brg:brg_01…`.
- Every token we issue has mandatory `iss`, `sub`, `aud` (single string, never an array), `iat`, `exp`, `jti`, and a JOSE header `typ` unique per credential kind (see §5). Verifiers reject a missing/foreign `aud` or `typ` (no warn-only path).
- The person (Clerk) token is never in this format and is never accepted anywhere except the Portal gateway → Core (CREDENTIALS rule P1).

## 3. Crypto (one choice each)
- Signatures: Ed25519, JWS compact, `alg: EdDSA`, `kid` = RFC 7638 thumbprint. No HMAC tokens, no RSA.
- Canonical JSON: RFC 8785 (JCS). Digest: `sha256:<hex>` of JCS bytes (manifests, configs, skills, catalogs).
- Secrets at rest we must keep: sealed with AES-256-GCM under a KEK from the service environment (Core: Portal signing keys, Railway refresh token; bridge: key store; apps: their own keys). Codes and opaque tokens we only verify: stored as SHA-256 digests.
- Primitives (JCS, digest, JWS sign/verify, key-set handling, `verifyGrant()`, `gate()`, `authorize()`) have ONE owner: package `@opt2-tealbrick/manifest` (REPOS.md). Copying them elsewhere is a CI failure.

## 4. Trust chain (who trusts which key)
```
Portal Root Keys (offline, 2: root-a + root-b; v0.1.11) ──signs──► key-set statement (tb-keyset+jws: the Portal signing keys + status, seq)
Portal signing key K12 (sealed in Core, listed in the statement) ──signs──► workspace config (for the bridge)
                                      ├─signs──► instance slice (per app, relayed by the bridge)
                                      ├─signs──► grants (agent→app, app→app)
                                      └─signs──► person tickets (launch | keys)
Bridge key (generated in the bridge, never leaves it) ─signs─► agent sessions, call proofs, bridge assertions (to Portal)
Instance key (generated in each app instance) ─signs─► instance assertions (to the bridge)
Agent connection key (generated on the agent machine) ─signs─► agent assertions (to the bridge)
```
- v0.1.11 (C62/C63): the root PUBLIC keys are release data (`PORTAL_ROOT_KEYS` in `@opt2-tealbrick/spec`, embedded in every bridge and SDK build; dev-channel builds pin the dev pair, stable builds pin only the production pair). The trusted Portal key set is derived ONLY from the newest valid root-signed key-set statement (`portalKeySet` in the enrolment response, every config and every slice): `seq` monotonic, pinned in the bridge's sealed state and the app store. A K12 holder can sign configs but can no longer change the key set. Root change = spec + bridge/SDK release (no in-band root rotation). Details and ceremonies: CREDENTIALS §9.5. No transition path since 0.1.26 (C133).
- Before v0.1.11: the bridge learns Portal's key set in the enrolment response (TLS to the Portal domain) and pins it; apps learn it from the deploy env (`TB_PORTAL_KEYS`, public values only) and from instance slices.
- Rotation: a new Portal key is announced (`pending`) in a key-set statement ≥ 24 h before first use; retired keys stay verifiable for tokens until every token they signed has expired (≤ 12 h); configs and slices are accepted only from `active` or `pending` keys of the newest statement.
- Standalone (leaving Portal): Portal signs a final config with `standalone.issuer = <bridge key>`; from then on the bridge signs configs/slices/grants/tickets with its own key and apps accept it because a Portal-signed slice named it (BRIDGE.md §Standalone).

## 6. The ONE grant (K10)
Claims: `iss` (`tb:portal`, or `tb:brg:<id>` in standalone), `sub` (`tb:agt:<id>` or `tb:ins:<id>`), `aud` (`tb:ins:<target>`), `ws`, `cnf: {brg: <bridge id>}` (only the workspace bridge may present it, proven by its call proof), `crud` (subset of `["create","read","update","delete"]` = edge ceiling), `mode` (`free|bound`), `held` (hold families held for this caller), `caps` (Free caps), `wf` (Bound: allowed operation ids), `polrev` (policy revision), `iat`, `exp` (= iat + 12 h), `jti`.
- Minted by Core for every licensed, unpaused edge (agent→app) and every manifest-declared companion edge (app→app; companion grants stay minted while paused — pause is status-only for them, C359a), delivered inside the signed workspace config, re-minted at half-life (< 6 h left). Agents NEVER hold grants: the bridge attaches the grant to the forwarded call. A companion grant is held by the calling app (from its slice) and presented to the bridge, which forwards it with its call proof.
- Scopes: the APP is the authority for scope assignments (DECISION-LOG "Configure opens the app, which is the authority for its scopes"). The grant carries the CRUD ceiling and mode; the app holds per-scope access (Connect: per-account tier; Knowledge: per-area read/write) created from the manifest's `scopes[].defaultGrants` when an edge first appears, edited in the app's Configure UI. Effective access = `grant.crud ∩ operation.crud ∩ scope access` (computed by `authorize()`). The canvas line shows a display-only summary the app reports through the bridge status report (labels only, no third-party identifiers).
- Licence-last (R4): an app may be deployed and its edges drawn while unpaid; Core mints no grants / launch tickets / hook activations for it until entitled; the GUI shows the glowing pay pill.
- Licence gate lives in Core only: no entitlement → no grant, no slice entry for edges, no launch ticket. Bridge and apps never check licences.
- Verification: signature with trusted Portal key set (or standalone issuer), `typ`, `aud` = own instance, `exp`, `cnf.brg` = the bridge that signed the call proof. No introspection, no online check.

## 7. Decision: one grant-verify function, bridge gate, app mode decision (C10)
All in `@opt2-tealbrick/manifest` (pure, synchronous, no I/O), so bridge and app run identical code:
- `verifyGrant(token, ctx) → VerifiedGrant | Refusal` — signature with trusted key set, `typ`, `aud` = target instance, `exp`, `cnf.brg`, issuer. Used by the bridge before forwarding and by the app SDK again on receipt (re-verify).
- `gate(input) → { decision: "pass" | "refuse", reason }` — run by the BRIDGE on every routed call (MCP, relay, app→app) for every harness: (1) paused (workspace kill switch, agent, connection, instance) → refuse; (2) grant valid (`verifyGrant`) → else refuse; (3) `op.crud ⊆ grant.crud`, op is agent-audience, op's `scopeType` is one the target manifest declares → else refuse; (4) Bound, or (v0.1.19 C111a) any grant whose `wf` is non-empty: `op.id ∈ grant.wf` → else refuse; then the bridge runs before/context hooks (fail closed) and forwards. Exception: the standard op `tb.hold_status` passes step (3) with any valid grant (it returns only the caller's own holds).
- `authorize(input) → { decision: "run" | "hold" | "refuse", reason, holdFamily? }` — the MODE decision, run by the APP SDK before executing, because its state (scope access, caps counters, holds, receipts) lives in the app: (0) paused per the latest instance slice (workspace, agent) → refuse; (1) `verifyGrant` again; (2) scope access from the app's scope store: `op.crud ⊆ grant.crud ∩ access.crud` → else refuse; (3) effect / hold family ∈ `grant.held` → hold; (4) Free caps exceeded (receipts counters) → hold; (5) run. `money` is always held. No standing grants (C8): a hold is approved once per call; there is no "always allow" record.
Vocabulary (`free|bound`; effects `read|write|outward|destructive|money`; hold families `first_contact|profile_change|live_call|destructive|money`) is defined ONCE in `@opt2-tealbrick/manifest`; Core stores policy values but holds no literals of its own. Holds and receipts live only in the app (SDK receipts table).

## 8. Call path and hook envelope (bridge ↔ app)
- Agent → bridge: MCP (Streamable HTTP) with `Authorization: Bearer <agent session>`.
- Bridge → app (private network, HTTP): `POST <internalUrl>/tb/v1/ops/<operationId>`; headers `Authorization: Bearer <grant>`, `TB-Call: <call proof JWS>` (bridge key; claims `aud` target, `call` id, `gjti` = the grant's `jti`, `op`, `in` = sha256 of JCS input, `ctx` = sha256 of context, `exp` 60 s), body `{ input, context, idempotencyKey? }` (the agent may pass `_meta["tealbrick/idempotencyKey"]` on the MCP call; otherwise none).
- Hook call: `POST <internalUrl>/tb/v1/hooks/<hookId>` with `TB-Call` (claim `phase`), body `HookRequest { phase, call: { id, ws, caller {type,id,mode}, target {instance, product, op, crud, effect}, input? }, context }`. Responses: before → `{ allow: boolean, reason? }`; context → `{ add: { "<product>.<key>": JSON } }` (namespaced, merged into `context`); after → `{ output?, redactions? }`. `context` is an open JSON object (extensible; Rules adds `onBehalfOf` later without bridge change; opt2 does not set it).
- Order: before hooks (ascending `order`, then product id) → context hooks → target app → after hooks. Any before or context hook error/timeout (2 s) → refuse (fail closed). After hook error → output withheld, call marked `after_failed` in the receipt (the action is not undone).
- Errors: one envelope everywhere (also device-flow polling): `{ "error": { "code": "<snake_case>", "message": "...", "requestId": "...", "details"?: { } } }`.

## 9. Agents, connections, devices
- Agent (card) ≠ connection ≠ device-flow request ≠ person. An agent card can have several connections (e.g. five Mac minis). Owner-added agents are `free`; `bound` agents are created by apps (next wave) — the mode exists in opt2.
- The workspace bridge is deployed at onboarding step 1, right after the infrastructure link (B1), so every connection path below works before any app exists.
- Every agent connection is created by the owner in the Portal browser, whatever the harness, and recorded as one Connection Registry row `{con, agt, method, verifier}`:
  - key connection (TBD, `tealbrick` CLI agent mode, Claude Agent SDK / Eve kits): the agent machine generates K4, starts RFC 8628 device flow at Core with its public key, owner approves in the browser in one click → Core registers `{con, agt, method: key, publicKey}` → it appears in the next config → the agent exchanges a K4-signed agent assertion (RFC 7523 jwt-bearer) at the bridge `/oauth/token` for K5.
  - OAuth connection (Claude Desktop / Codex desktop remote MCP connector) — C4: the harness runs MCP OAuth 2.1 against the deployed bridge (bridge = authorization server for its own MCP resource: RFC 9728 protected-resource metadata, RFC 8414 AS metadata, RFC 7591 DCR, PKCE S256). The bridge's authorize page asks for the agent pairing code (K2b) shown on the agent card in Portal; the bridge verifies it offline (Portal key, `aud` = this bridge, unused `jti`), creates `con` (method `pairing`) locally, issues K5 access + rotating refresh, and reports the new connection in its next ack; Core records it. J1 no-terminal path (R3): the authorize page offers 'Approve in Portal' — browser redirect to Portal with a bridge-signed state, the signed-in owner picks/creates the agent card and approves, Portal form-POSTs a fresh K2b back to the bridge, verified offline; copy-paste of the code is the fallback. The approval screen shows the OAuth `redirect_uri` host and the DCR client name marked "unverified"; Core checks that the bridge's workspace belongs to the approving person (S3).
- Local bridge (C5): the same bridge package in `relay` mode inside the `tealbrick` CLI: serves stdio MCP to the harness, authenticates upstream to the deployed bridge as the agent (K5), holds no grants, no keys, no config, and duplicates no checks. Enforcement happens only in the deployed bridge. Exception: a bridge that is itself enrolled (own infrastructure) is a full bridge, whatever machine it runs on.
- A person credential is never input to any agent path (no exchange, no derivation, no forwarding).

## v0.1.80 (C373, G-2) — slice `topology` (display only; label 0.1.80, number set at merge)
Normative.
1. **What.** `InstanceSlice.topology?: SliceTopology` is a DISPLAY copy of the workspace grant picture in compact tuple form (bounds `TOPOLOGY_MAX` = the schema `maxItems`; every tuple has exactly its arity, schema `prefixItems` + `items: false`):
   - `v`: `1`.
   - `instances[]` (≤ 40): `[ins, product, name, version]`; `name` = the manifest name (display copy, ≤ 80), `version` = the deployed release.
   - `edges[]` (≤ 600, one per agent → app grant): `[agentIdx, instIdx, crud, mode, held, wfCount, paused]`. `agentIdx` indexes the SAME slice's `agents[]` (so M-TP-1 requires `needsAgentDirectory`); `instIdx` indexes `topology.instances`; `crud` = the letters of the granted actions in the order c, r, u, d (`^c?r?u?d?$`); `mode` `"f"` (free) or `"b"` (bound); `held` = a non-negative integer bitmask over `MANIFEST_HOLD_FAMILIES` order (bit i = family i); `wfCount` = the length of the grant's op list (0 = all ops, no list; ≤ 128); `paused` `1` when the agent, the instance or the workspace is paused, else `0`.
   - `companions[]` (≤ 100, app → app grants): `[fromIdx, toIdx, crud, opsCount]`; both index `topology.instances`; `opsCount` as `wfCount`.
   - `connections[]` (≤ 300): `[con, agentIdx, method, status]`; `method` `"k"` (key) or `"p"` (pairing); `status` `"a"` (active) or `"r"` (revoked).
   - `truncated?: true`: Core cut at least one list at its bound.
2. **Indexes.** A reader MUST check every index: 0 ≤ idx < the length of the list it indexes (`agents[]` of the same slice, or `topology.instances`). A row with an index out of range is dropped, and the reader treats the topology as truncated. Core writes only valid indexes; the rule protects readers from an inconsistent slice.
3. **Hold-family bits.** `MANIFEST_HOLD_FAMILIES` is APPEND-ONLY: a new family is added at the end (a new high bit); a family is never reordered or removed. A reader ignores bits above the families it knows (`topologyHeldFamilies`). `held` ≤ `TOPOLOGY_HELD_MASK_MAX` (31 bits).
4. **Consent.** Core puts `topology` into a slice ONLY when the app's manifest declares `needsTopology: true` AND the owner granted the consent `topology` (`ConsentKind`, PORTAL-API `instances.consent`). The deploy review names it (`CatalogEntry.consentsAsked`): "This app can see which agents and apps have access to what in this workspace". An update whose target manifest adds the flag needs a new consent (`Instance.updateConsentsAsked`). Without the consent the field is absent (not empty). A revoke removes it from the next slice.
5. **Never authorize.** The bridge and the SDK never read `topology` to authorize. Apps MUST NOT use it to authorize; access comes only from the verified grant (§6, §7). It is stale until the next slice revision; Core re-mints the slice when the picture changes, like any other slice change.
6. **Content.** No labels beyond instance `name` and `version`. No agent names (they are in `agents[]`), key names, persona, endpoints, secrets, jtis or other token data, and no op ids (only counts).
7. **Size.** Core counts the topology in its measured worst-case slice and config (`SLICE_CORE_MAX_CHARS`, `CONFIG_CORE_MAX_BYTES`, PORTAL-API "Config size"), measured on the RESULT of the change with the kill-path maxima: every edge `paused` 1, every connection `"r"`, `held` at all known families (kill-path changes never grow it past this).
8. **Open question (OQ-C373-1, packages lead).** At the full bounds the topology ALONE is 41,119 JSON chars (54,826 base64; measured by `test/topology.test.ts`: names at 80, products at 32, `held` 255, counts 128), which passes `SLICE_CORE_MAX_CHARS` (52,000) before the `needsAgentDirectory` directory is counted. So in a workspace near the bounds rule 7 makes ordinary owner changes refusable for the Governance app's slice. A follow-up decides: smaller bounds, or Core cuts lists to fit (`truncated: true`) instead of refusing.

## v0.1.82 (C373 P1) — per-workflow companion grants (Core)
Goal: the BRIDGE limits each active workflow of a caller app to the ops and crud the owner approved for THAT workflow. Non-goals: scope instances per workflow (scope rows stay keyed by the caller instance, honest label), agent grants, hooks, held families, Rules, P4 context semantics. Revised after the C5 security review and lead §11 (2026-10-27): fixes are marked with their finding id.
- **§6 addition.** A companion grant may carry `wfl` (CREDENTIALS v0.1.82). Grants with `wfl` are minted ON DEMAND (never in a slice or the config, I8 unchanged for base grants), live `WORKFLOW_GRANT_TTL_SEC` (900 s), and are withdrawn by config records, not by `revoked.jtis`.
- **Storage.** New table `companion_workflow_grants(ws, from_ins, wfl, title, reason, targets JSON, state requested|applied|rejected|withdrawn, applied_targets JSON, applied_title, applied_reason, applied_digest, pending_digest, pending_targets JSON, draft_id, rejected_digest, requested_at, applied_at, withdrawn_at, changed_at)`, unique (ws, from_ins, wfl); plus `workflow_gate_on(ws, from_ins, to_ins, since)` (sticky gate, below); a migration is appended. Rejected and withdrawn records without a pending draft are kept 30 days for the owner's list, then deleted. Minted grants are recorded like other K10c grants (issued credentials).
- **Canonical body and digest (C5 bound payload).** Normalise the request: `targets` sorted by `product`; `ops` sorted and unique; `crud` unique in the order create, read, update, delete; `reason` omitted when absent or empty. Body = `{ins, wfl, title, targets, reason?}` (`ins` = the verified caller). Digest = `sha256:` + lower-case hex SHA-256 of its JCS (RFC 8785) UTF-8 bytes (`Sha256Digest`); reference rows in `examples/workflow-grant-digest.cases.json`.
- **Request (`bridge_api.workflow_grant_request`).** Refuse unless: the bridge is the workspace bridge; `ins` is an installed instance of that workspace and not paused (409 `conflict`, `details.reason` "paused"); the caller's INSTALLED manifest has a one-product companion entry with `perWorkflow` for every target (else 400 `validation_failed`, `details.pointer` `/targets/<i>/product`); the target is deployed with an ENABLED companion edge from the caller (else `validation_failed`); `ops` ⊆ `perWorkflow.operations` and `crud` ⊆ `perWorkflow.crud` ∩ edge crud (pointer to the first offending item; `tb.*` ops always refused); limits `WORKFLOW_GRANT_REQUEST_LIMITS` (1..8 unique targets, 1..64 ops each); `title` (1..120) and `reason` (≤ 280) match `WORKFLOW_GRANT_TEXT_PATTERN` — no control, format (bidi included) or invisible character (S3-4); at most `WORKFLOW_GRANTS_MAX` (500) requested + applied records per caller instance (a new `wfl` beyond it → 409 `workflow_grants_full`). A request whose digest equals the record's `rejected_digest` → 409 `conflict` (`details.reason` "rejected"; S3-4: a rejected ask is not re-asked unchanged). The gate (below) is NOT required for a request: an owner may approve before every target re-releases.
- **Diff against the applied set.** Same digest as `applied_digest` → unchanged. Same digest as `pending_digest` → unchanged (same draft). Every requested target is in the applied set with `ops ⊆` and `crud ⊆` its applied values → the request's TARGETS become the applied set AT ONCE, no draft (a narrowing). The APPROVED `title` and `reason` stay (S3-4: a narrowing never relabels what the owner approved); `applied_digest` = the digest of `{ins, wfl, approved title, new targets, approved reason?}`. Every narrowed or dropped target gets a withdrawal record with its `aud` — a kill path, never size-refused. Anything else (no applied set, a new target, a new op or crud) → a Portal draft (`DraftCreatedByApp`) with exactly one step `companions.workflow_grant_set {ws, ins, wfl, title, targets, reason?, digest}`; `pending_*` = it; an older open draft of the same record is rejected by Core (superseded). Draft limits per caller instance `WORKFLOW_GRANT_DRAFTS` (S3-4): more than 10 open → 409 `conflict` (`details.reason` "too_many_open_drafts"); more than 30 created in 60 min → 429 `rate_limited` + `Retry-After`. The applied set stays as it is until the owner applies. Audit `workflow_grant.request` with the outcome.
- **What the owner sees.** Draft title and step summary per target: "<app name> asks: workflow '<title>' may <crud words> on <target app>: <ops>", the app's `reason` marked "reported by the app", and the digest. `looseningOf` lists ONE item per widened op (an op not in the applied set for that target) and ONE per widened crud action per target; `drafts.apply` needs every item id in `confirmLoosening` (confirm per widened item).
- **Apply (`companions.workflow_grant_set`, `draftable: "app_only"`, only as that draft step).** Recompute the digest from the step input; it must equal the step's `digest` and the record's `pending_digest`, else `draft_invalid` (nothing applied). Re-run every request check against the CURRENT state (installed manifest, edge, ceiling). Then `applied_*` := the step (title and reason included), `state` = `applied`, `pending_*` cleared; any part of the old applied set that the new one does not contain gets a withdrawal record. Audit `workflow_grant.set`. A direct browser call of the row → 403 `forbidden` (`details.reason` "apply_via_draft"); `drafts.create` / `update` / `import` refuse the op (`draft_op_not_draftable`); an app-created draft cannot be edited (`draft_state`) or exported (`recipe_not_portable`).
- **Reject (`drafts.reject`).** `rejected_digest` := `pending_digest`, pending cleared; `state` = `rejected` when nothing is applied, else it stays `applied`.
- **Kill path (withdrawals; `KILL_PATH_OPS`, never refused by the size rule).** The triggers are exactly these (lead §11.1): (1) `companions.workflow_grant_revoke` (owner) and `bridge_api.workflow_grant_release` (app): state `withdrawn`, pending draft rejected, one record `{sub, wfl}` (no `aud`). (2) A narrower request or an apply that narrows: records per narrowed target (`aud`). (3) **C1, app update narrows:** when the caller instance is updated or rolled back, Core compares every applied record with the NEW release's `perWorkflow` per product and drops each op, crud action and target outside it, in the same transaction as the update; a target with no op left is dropped; a record with no target left is `withdrawn`; records as in (2); audit `workflow_grant.withdraw` (reason `app_update`). (4) The companion edge disabled (`edges.update {enabled: false}`) or removed, or the target instance removed: that target is dropped from every applied record of the caller (record with `aud`; the target leaves `workflowGrantEdges`). (5) The caller instance uninstalled: its records are deleted (its slice, keys and `workflowGrantEdges` entry leave the config, so the bridge refuses its assertions). (6) The workspace kill switch (`workspaces.pause`): `wflEpoch[sub]` = now for EVERY caller instance (every cached grant dies); records stay `applied`, and Core mints none while the workspace is paused. NOT a trigger: the wildcard consent revoke (`instances.consent` for `tb.holds_pending`) — it never touches workflow grants (lead §11.1). An instance pause keeps the records (pause is status-only, C359a; the bridge refuses calls).
- **Base re-mint bumps the epoch (S2-1).** Any change that re-mints a caller's BASE companion grant with other claims (other than `iat`, `exp`, `jti`) — `appsPolicy.held`, `polrev`, an edge's crud or enabled flag, an update of caller or target, a gate change — sets `wflEpoch[sub]` = now for every affected caller in the SAME transaction and config revision (kill path). So a held-family tightening reaches cached workflow grants within one config ack, and every re-fetched grant carries the new claims. The bridge also refuses a workflow grant whose `held` lacks a current family (BRIDGE §8.6 rule 2.4(d)).
- **Withdrawal records.** Written in the same config revision as the change: `{sub: tb:ins:<caller>, wfl, aud?, at: now}` in `workflowGrantsWithdrawn`; records and epochs are pruned once `at + WORKFLOW_GRANT_TTL_SEC + 2 × LEEWAY_S` has passed (S3-1). When a caller would have more than `WORKFLOW_WITHDRAWN_MAX` (64) live records, Core instead sets `wflEpoch[sub]` = now and drops that caller's records with `at ≤` it (every grant they cover is covered by the epoch); the SDK re-fetches and still-applied workflows re-mint at once. `workflowGrantEdges` (S3-3) lists, per caller, the target instances whose companion edge is enabled and licensed and whose entry has `perWorkflow`. These three fields are sent only to a bridge that declares `app_workflow_grants`.
- **Mint (`bridge_api.workflow_grant_get` with `aud`).** First the gate for that target (below; workspace paused → 409 `conflict`, `details.reason` "paused"); then the record: none / `requested` / `rejected`, or the target not in the applied set → 404 `workflow_grant_missing`; `withdrawn`, or no enabled licensed companion edge to `aud` → 410 `workflow_grant_withdrawn`. C1 mint-time re-check: `wf` = applied ops ∩ the CURRENT `perWorkflow.operations` of the caller's installed manifest entry for that product (+ `tb.hold_status` when that entry's `operations` list it); `crud` = applied crud ∩ edge crud ∩ current `perWorkflow.crud`; an empty `wf` or `crud` → 404 `workflow_grant_missing` (and the record is narrowed as in C1). Claims: `sub`, `aud`, `ws`, `cnf.brg`, `mode: "bound"`, `held` = `appsPolicy.held`, `caps: {}`, `polrev`, `prd`, `wfl`, `iat`, `exp = iat + 900`, new `jti`. Without `aud`: status only, never a grant.
- **Mint/withdraw race (S2-2).** Mint and every withdrawal of one record are SERIALIZED: the mint reads the record, the live records and the epoch, and fixes `iat` inside the same transaction that holds the record's row lock (the lock every withdrawal of that record, and every epoch bump of that caller, takes). After signing, Core re-reads the record's `changed_at` and the caller's epoch; when either changed at or after `iat`, it discards the grant and answers from the new state (no grant). Row `C-WFL.mint_race`.
- **Reuse cache (S3-2).** Core reuses a minted grant for the same (caller, wfl, aud) and the same claims EXCLUDING `iat`, `exp` and `jti` while more than 450 s are left, and NEVER hands out a cached grant that a live record or epoch covers (`iat ≤ at` / `≤ epoch`): it mints a new one instead.
- **Gate (capability, C354; lead §11.2).** Core mints a grant with `wfl` for a target only when ALL hold at mint time: the workspace bridge declared the bridge cap `app_workflow_grants` in its last authenticated status report; the CALLER instance's reported app caps (`StatusReport.apps[].caps`) include `app_workflow_grants`; the TARGET instance's reported app caps include `grant_wfl` (its verifier knows the closed-set `wfl` claim). No min-SDK constants. Gate off → 409 `workflow_grants_unsupported` with `details.product`; standalone has no issuer.
- **Fallback while the gate is off, and the sticky gate (S1-1).** App caps are a self-report (advisory; they MUST NOT widen access, SDK-API v0.1.54). So the fallback never restores the ceiling: while the gate is off for a (caller, target) pair that was never gated on, Core mints that companion entry's BASE grant with `wf = operations ∪` the union of the ops CURRENTLY APPLIED for that target across the caller's workflow records, and `crud = edge crud ∩ crud` (the BASE crud, unchanged: C5 delta S2-A — the fallback never adds crud, because ops and crud combine freely in one grant and a DYNAMIC op would resolve to any added action up to its `crudCeiling`). An applied op is added to the fallback only when it is STATIC (no `crudCeiling`) and its crud ⊆ the base crud; any other applied op (dynamic, or needing more crud) is NOT in the fallback and works only under a workflow grant once the gate is on. An op the owner never approved, rejected, or revoked is never in it; a change of the applied set re-mints that fallback base grant (a narrowing withdraws the old jti via `revoked.jtis`, kill path). The first time Core mints a workflow grant for a pair it records `workflow_gate_on(from_ins, to_ins)`; from then on the pair is STICKY ON: no later report (a cap dropped, a target or caller rollback, a bridge that loses the cap) brings the fallback back — the base grant keeps `wf = operations` and workflow calls fail closed (`workflow_grants_unsupported`) until the inputs return. Only a reinstall (new instance id) starts a pair again. When a pair turns on, Core re-mints the base grant with `wf = operations`, withdraws the fallback one (kill path) and bumps the epoch (S2-1). C5 delta S2-B: a pair turns on ONLY at Core's first mint of a workflow grant for it; a cap report on its own (caller, target or bridge cap appearing, disappearing or flapping) NEVER re-mints a base grant and NEVER bumps an epoch — the fallback base grant changes only when the APPLIED set changes, and becomes `wf = operations` only at that first mint. While the gate is off, an op in the fallback is usable by EVERY workflow of the caller for that target (the review page says so, PORTAL-API v0.1.82).
- **Companion edge crud.** `syncCompanionEdges` sets the edge crud of an entry with `perWorkflow` to `crud ∪ perWorkflow.crud` (MANIFEST §9.1); the base grant is still `edge crud ∩ crud` (the fallback never adds crud: C5 delta S2-A).
- **Config size (PORTAL-API v0.1.82).** The worst-case measure counts, for EVERY instance, `WORKFLOW_WITHDRAWN_MAX` records at their largest serialized size (40-char `wfl`, with `aud`, largest `at`), one `wflEpoch` entry, its `workflowGrantEdges` entry with every possible target, and every base grant at the upper bound `wf = operations ∪ perWorkflow.operations` (the fallback can reach at most that, since applied ops ⊆ `perWorkflow.operations`). Workflow grants themselves are never in the config or a slice. Executable model: `test/killpath-model.test.ts` (RM-24c, P1 rows).
- **Hooks (C3).** The bridge gives Rules hooks the verified `call.caller.workflow`; Core adds nothing to `hooks[]`.
